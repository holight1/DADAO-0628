## 背景

架构师起草了一份准备提交给 wiki 团队的架构扩展提案
（`docs/proposals/cfx-mem-cfx-mask.md`）：新增一个跨 cfx 访存屏蔽寄存器
`mem_cfx_mask`（`cg0-3/rc12`），堵住"普通 load/store 拼核内地址绕过既有
六个跨 cfx 功能调用指令屏蔽"这个缺口。这份提案**尚未被任何人独立核实
过**——本任务要求一个独立 subagent 从零核实，不采信提案文档自己的
论证，找出真正的问题（如果有）。

## 目标

1. **独立核实提案引用的每一条 wiki 原文**：直接读
   `~/DADAO-wiki/DADAO-12-SEE-主管系统运行环境.md` 第73行、第269-281行、
   第746-747行（提案引用的具体行号），确认提案摘录/转述的文字与 wiki
   原文逐字一致，没有断章取义或曲解。
2. **独立验证提案声称的"缺口"是否真实存在**：提案核心论点是"六个
   功能调用类指令的跨 cfx 屏蔽机制不覆盖普通访存指令拼核内地址访问其它
   cfx 这条路径"。通读 wiki 第2章（核内地址空间）、第5章（异常进入
   流程完整伪代码，尤其步骤1的核内地址空间分支）和 cg0-cg3 寄存器表
   全文，确认：
   - 是否真的没有任何其它机制（本提案没提到的）已经覆盖了这条路径；
   - 提案给出的伪代码插入点（"reserved cfxcode 判断之后、正常路由之前"）
     是否真的是唯一合理的插入点，有没有遗漏的分支或场景。
3. **独立评估提案本身的设计质量**：
   - 复位默认值"全1拒绝"是否真的和现有六个掩码一致（不是提案自己
     假设的，要真的去读那六个掩码各自的复位值定义核实）；
   - `rc12` 是否真的是 cg0-3 当前空闲的下一个槽位（数一遍 rc1-11 是否
     真的都被占用，没有别的隐藏空位或冲突）；
   - "复用既有 CFXMEM 异常原因、不新增新原因编号"这个选择是否合理，
     还是应该有自己独立的异常原因（提案没有充分论证这一点，需要独立
     判断）；
   - 提案排除的范围（"不涉及 PTBR 开启后的物理内存隔离"）划得是否
     合理，是否存在提案没意识到的、这个新掩码可能带来的意外副作用
     或安全性反效果（例如：新增的屏蔽会不会反而破坏某个现有 K1/K2/K3
     已经依赖的隐式行为——虽然提案声称"不要求现有实现做任何改动"，
     这个结论本身要独立核实，不能只信提案的自我声明）。
4. **寻找提案没有考虑到的反例或场景**：例如——
   - `cfxld`/`cfxst` 访问的"cfx 内部存储块"和"核内地址空间"是不是
     完全同一回事？如果不是，提案"cfxld/cfxst 已经有自己的掩码所以
     不用管"这个论断是否站得住；
   - reserved cfxcode（7-14、19-61）的 ILLI 路由和本提案新增的 CFXMEM
     路由，两者的触发顺序/优先级是否有冲突或歧义；
   - 如果一个 cfx 的 hypv mode 掩码被设成全0（允许所有跨 cfx 访存），
     而 supv mode 掩码是全1（拒绝），这种"上级模式更开放、下级模式更
     严格"的配置在架构上是否自洽，还是暗示掩码应该有某种层级继承
     关系（提案没有讨论这一点）。
5. **给出独立结论**：提案是否站得住脚、是否有需要修改的地方（哪怕是
   小的行文/引用错误）、是否有本任务发现的、提案作者没意识到的实质性
   问题。

## 实施记录

**完成，2026-07-31**。评审记录见
`docs/proposals/cfx-mem-cfx-mask-review.md`（独立 subagent 撰写）。

**结论摘要**：
- 6 处 wiki 引用逐字核实，5 处完全准确，1 处行号笔误（"第269行"应为
  "第271行"，已在提案文件内订正并标注）。
- **核心缺口（普通访存绕开跨cfx功能调用屏蔽）独立核实为真实存在**，
  但范围需收窄：能被绕过的是 cfx"内部存储块"（SRAM），**不包括**
  cg/rc 寄存器组（寄存器组只能经 `cfx2rd`/`cfx2rc` 的 `cg:rc` 索引
  访问，wiki 全文未定义其映射进核内地址空间），提案 §1 动机场景措辞
  "核内寄存器/存储块"存在夸大，应改为只提"内部存储块"。
- **最严重发现**：提案 §2.2 给出的插入点技术上不完整——`if cause ==
  CFXMEM` 这个分支只有在访问本身已经非法（wiki 第73/382行明确写
  "非法访问时"）才会被进入；对一次目标合法、仅未被授权的访问，
  硬件根本不产生 CFXMEM、不会进入这段伪代码，提案插入的检查是死
  代码。要让掩码真正生效，必须同时修改 §2.1/cg7 定义"何时判定为
  非法"的自然语言条件，提案目前完全没有触及这一层，只改了下游的
  路由伪代码。
- **另一处发现**：新插入的 `temp_cfx_code <= inner_cfx_code` 自称
  "与 reserved cfxcode 路由到当前 mode monitor 的既有惯例一致"，
  但核实 wiki 原文（第721-728、747-753行）reserved cfxcode 和六个
  既有掩码拦截路由的实际是"当前运行模式对应的 monitor"（`case
  inner_run_mode of...`），不是 `inner_cfx_code`——两者只在恰好
  处于 mode monitor 自身时相等，在其它 cfx（如 cfx_ptw）处理程序
  内触发时会给出不同目标，提案的"一致"断言不成立。
- 复位默认值全1、`rc12` 空闲槽位、PTBR 排除范围、"层级不一致"场景
  （hypv开supv关）经独立核实均**合理/不构成新问题**（层级不一致是
  wiki 现有六个掩码本就有的固有特性，非本提案引入）。
- 结论：**提案的核心动机站得住脚，但当前给出的具体修补机制不完整、
  不能以现在的形式提交 wiki 团队**，需按评审文件 §6 的建议修订
  （收窄动机场景措辞、补齐触发条件层面的修改、重新论证路由目标）
  后再考虑对接 wiki 团队。
- 对提案本体只做了两处最小、已标注的改动（状态行加评审指针、行号
  笔误订正），核心论证段落未动，改动细节见评审文件 §5。

### 架构师复核与提案修订（2026-07-31）

独立验证了评审最关键的发现（§3-B）：直接重读 wiki 第706-753行完整
步骤1伪代码，确认 `elif mem_access: if cause == CFXMEM:` 确实是**读**
一个已经确定的值，`cause` 变成 `CFXMEM` 由第73/382行"非法访问时"这条
自然语言定义在别处决定——v1 提案把新检查插在这个分支内部确实执行不到，
评审的发现成立，不是评审自己的误判。

据此把提案改到 v2（`docs/proposals/cfx-mem-cfx-mask.md`）：**不再新写
路由逻辑**，而是把新掩码表达成"§2.1/cg7 的'何时非法'定义新增一条件"，
让既有的 `else: temp_cfx_code <= addr[47:42]`（本来就正确地把任何
CFXMEM 都路由到目标 cfx）原样处理路由——这同时解决了 §3-B（触发条件
补齐）和 §3-C（不再需要新路由分支，也就不存在"该路由到 inner_cfx_code
还是 mode monitor"这个 v1 自己制造出来的选择困境）。另外按 §3-A 收窄
了动机场景措辞（只谈"内部存储块"，不再提"寄存器"）、补了"两把锁配置
需一致"的操作规范提示、在开放问题里补了 `rc0` 作为 `rc12` 的备选。

结论：**评审的核心发现（提案技术上不完整）确认成立，已修订为 v2**。
v2 是否真的完全站得住还有待下一轮独立核实，但至少 v1 已知的两个致命
问题已经解决。
