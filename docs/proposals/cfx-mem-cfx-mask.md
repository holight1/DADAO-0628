## 1. 动机：一个真实存在、目前完全未被屏蔽的跨 cfx 访问面

wiki 已经为**功能调用类指令**建立了一套完整的、按运行模式（user/jail/
supv/hypv）独立配置的跨 cfx 访问屏蔽机制——`DADAO-12-SEE-主管系统运行
环境.md` 第269-281行（cg0，user mode 为例，cg1/cg2/cg3 对 jail/supv/hypv
分别定义相同的一套）：

| rc | 寄存器 | 屏蔽的指令 |
|----|--------|-----------|
| 2 | `cfx2rd_cfx_mask` | `cfx2rd`（读其它 cfx 寄存器） |
| 3 | `cfx2rc_cfx_mask` | `cfx2rc`（写其它 cfx 寄存器） |
| 4 | `cfxld_cfx_mask` | `cfxld`（读其它 cfx 内部存储块） |
| 5 | `cfxst_cfx_mask` | `cfxst`（写其它 cfx 内部存储块） |
| 6 | `trap_cfx_mask` | `trap`（功能调用陷入其它 cfx） |
| 7 | `escape_cfx_mask` | `escape`（退出到其它 cfx，非本文讨论重点） |

这六个寄存器共享同一套语义：0=允许当前 mode 对目标 cfx 执行该指令，
1=禁止；复位值全1（默认禁止一切跨 cfx 访问，需要显式授权）；自身
cfxcode 对应位硬件忽略。

**但 wiki 同时定义了另一条完全不经过这套机制的跨 cfx 访问路径**：
第73行，"核内地址空间" 一节明确——

> 对核内地址空间进行非法访问时，会触发对应核芯功能扩展的 CFXMEM 异常。
> 核芯功能扩展由地址高 6 位 `addr[47:42]`（即 cfxcode）确定。

以及 SEE §5 步骤1完整伪代码（第746-747行）：

```
// 核内地址空间异常
if addr[47:42] ∈ {7..14, 19..61}:       // reserved cfxcode → ILLI
    ...
else:
    temp_cfx_code  <= addr[47:42]       // 正常路由
```

也就是说：**普通的 `ldb`/`ldw`/`ldt`/`ldo`/`stb`/`stw`/`stt`/`sto`（以及
它们的 `_rb` 多字变体）在 PTBR 未开启时，只要地址的高6位 `addr[47:42]`
写成目标 cfxcode，就能直接读写目标 cfx 的核内地址空间**——只要该
`(cg,rc)` 对目标 cfx 确实存在（否则触发 CFXMEM），完全不经过上面那套
已经为"功能调用类指令"建好的跨 cfx 授权检查。换句话说，**同一个"跨 cfx
访问"的语义动作，走 `cfx2rc`/`cfx2rd` 这类专用指令会被 mask 拦截，走
普通 load/store 拼地址反而畅通无阻**——这不是刻意设计的"两条路一样安全"，
而是 wiki 目前只顾及了"功能调用指令"这一类访问方式，没有覆盖"直接拼
核内地址访存"这一类。

**为什么这值得补上**：这条未被屏蔽的路径直接削弱了 cfx 模型本可以提供
的隔离强度。设想内核把不同的驱动/子系统各自绑定到不同的 cfx 处理
（`cfx_uart`、`cfx_timer`、`cfx_ptw` 本来就是独立的 cfx），并且已经用
`trap_cfx_mask`/`cfx2rc_cfx_mask` 精心配置了"谁能通过功能调用碰谁"——
只要攻击者（或者有 bug 的驱动代码）改用一条普通 `sto` 指令、把地址的
高6位设成目标 cfxcode，就能完全绕开这套精心配置的授权，直接读写目标
cfx 的核内寄存器/存储块。**这是一个真实的、当前架构里存在的隔离漏洞
形状**，不是假设性的。

## 2. 提案

### 2.1 新增寄存器

在 cg0-3（user/jail/supv/hypv）各新增一个寄存器，占用当前空闲的 `rc12`
（cg0-3 现有 rc1-11 共11个寄存器，第269行"以下11个寄存器"，rc12 是
下一个未分配槽位）：

| cg | rc | 寄存器名 | regname | 初始值 | 访问 | 说明 |
|----|----|---------|---------|--------|------|------|
| 0 | 12 | user mem cfx mask | `cfx_⟨cfxname⟩_user_mem_cfx_mask` | 全1 | RW | 普通访存指令（ldb/ldw/ldt/ldo/stb/stw/stt/sto 及其 `_rb` 多字变体）在核内地址空间（PTBR未开启）寻址其它 cfx 时是否允许，0=可，1=不可。自身 cfxcode 对应位硬件忽略 |
| 1 | 12 | jail mem cfx mask | `cfx_⟨cfxname⟩_jail_mem_cfx_mask` | 全1 | RW | 同上，jail mode |
| 2 | 12 | supv mem cfx mask | `cfx_⟨cfxname⟩_supv_mem_cfx_mask` | 全1 | RW | 同上，supv mode |
| 3 | 12 | hypv mem cfx mask | `cfx_⟨cfxname⟩_hypv_mem_cfx_mask` | 全1 | RW | 同上，hypv mode |

语义与现有六个跨 cfx 指令掩码逐字对齐：0=允许，1=屏蔽；复位全1（默认
拒绝，需要显式在目标 mode 下授权）；自身 cfxcode 对应位硬件忽略（访问
自己核内地址空间不受此寄存器影响，这与现有六个掩码"自身 cfxcode 硬件
忽略"的惯例完全一致）。

### 2.2 触发时机与 fault 语义

在 SEE §5 步骤1的核内地址空间路由伪代码（第746-747行）里，在
"reserved cfxcode → ILLI" 判断**之后**、"正常路由 `temp_cfx_code <=
addr[47:42]`"**之前**，插入一次检查：

```
elif addr[47:42] != inner_cfx_code
     and (cfx_⟨cfxname⟩_<mode>_mem_cfx_mask & (1 << addr[47:42])) != 0:
    cause <= CFXMEM
    ; 复用已有 CFXMEM 异常原因（第403/445/485/512/534/554/577/598行等
    ; 每个 cfx 异常原因表都已定义 CFXMEM = 1<<1，"访存地址"作
    ; excp_cause_info，本提案不新增异常原因，只新增触发这个既有原因
    ; 的一种新场景）
    temp_cfx_code <= inner_cfx_code  ; 路由回当前 cfx 自己的 monitor
                                     ; （与 reserved cfxcode 路由到当前
                                     ; mode 对应 monitor 的既有惯例一致）
else:
    temp_cfx_code <= addr[47:42]
```

不新增异常原因编号——CFXMEM（`1<<1`，"访问核内地址空间或内部储存块
故障"）已经是精确匹配这个场景的既有原因，本提案只是让它在一种新的、
此前从未被检查过的条件下也能触发。`excp_cause_info` 沿用既有约定
（"访存地址"，即触发异常的访存有效地址）。

### 2.3 与现有六个掩码的关系

不修改、不影响 `cfx2rd_cfx_mask`/`cfx2rc_cfx_mask`/`cfxld_cfx_mask`/
`cfxst_cfx_mask`/`trap_cfx_mask`/`escape_cfx_mask` 的任何既有语义——
本提案是**补齐第七种指令类别**（普通访存指令）的跨 cfx 屏蔽，不是替换
或统一现有六个。软件需要分别配置这七个寄存器才能得到完整的跨 cfx
访问控制矩阵（哪个 mode、通过哪种指令、能不能碰哪个 cfx）。

## 3. 明确不在本提案范围内

- **不涉及 PTBR 开启（虚拟地址）路径下的物理内存隔离**。本提案只覆盖
  "核内地址空间"（`addr[47:42]` 直接指定 cfxcode 的核内寻址），不
  涉及"某个 cfx 的代码能不能通过虚拟地址翻译访问某块物理 DRAM"这类
  更大的问题——那需要给 `cfx_ptw` 增加"按 cfx 限定可翻译的物理地址
  范围"这类机制，是一个量级完全不同、影响面大得多的设计，值得独立
  提案，不与本提案混在一起。
- **不改变 CFXMEM 本身的异常原因编号或既有触发条件**（访问不存在的
  `(cg,rc)`、试图写只读区域、reserved cfxcode 等既有场景不受影响）。
- **不改变 `cfxld`/`cfxst` 的既有跨 cfx 屏蔽机制**（那两条指令本来就有
  自己专属的掩码，本提案不重复覆盖）。
- **不对 K1-K3 现有实现提出任何改动要求**——DADAO-0628 项目目前的
  QEMU/gem5/Linux 实现完全没有使用跨 cfx 核内地址访问这个特性（内核
  代码只通过 `cfx2rc`/`cfx2rd` 访问其它 cfx 的寄存器），本提案是纯粹
  面向"如果 wiki 团队认可这个方向，未来的 OS 设计可以怎么用"的架构
  扩展建议，不是当前里程碑（K3/K4）需要的东西。

## 4. 开放问题（留给 wiki 团队决定）

1. **复位默认值是否应该是"全1拒绝"**：本提案沿用现有六个掩码的惯例
   （复位拒绝，需要显式开放）。这在架构上是"更安全的默认值"，但需要
   wiki 团队确认这个默认值选择和现有六个掩码的设计初衷一致，不是
   本项目单方面认定的。
2. **`rc12` 是否是 wiki 团队认可的下一个分配位置**：本提案假设 cg0-3
   的 rc1-11 之后顺序分配 rc12，但寄存器空间的分配权在 wiki 团队，
   这里只是一个建议位置。
3. **是否需要对称地在 hypv 之外新增更多访问维度**（例如是否要按具体
   访存宽度——字节/半字/字/双字——分别授权，而不是一刀切）：本提案
   采用最简单的"一个 mask 管所有宽度的普通访存"，如果 wiki 团队认为
   不同宽度需要不同粒度的控制，需要另行讨论。

## 5. 背景动机（非规范性，供 wiki 团队理解提出原因）

DADAO 的 cfx 模型（每个 cfx 独立的寄存器组、独立异常现场、独立跨 cfx
指令屏蔽）相比传统架构（x86 ring/ARM EL/RISC-V M-S-U 这类线性特权级）
提供了更细粒度的、硬件层面的跨域访问控制潜力——但目前这个潜力只覆盖
"功能调用类"指令，普通访存指令绕过核内地址空间时完全不受限制，是
这套潜力里一个具体、可修补的缺口。这个提案是 DADAO-0628 项目在推进
K3（Linux 内核移植）过程中，讨论"cfx 模型能否支撑比传统内核更强的
子系统隔离"时识别出来的具体切入点，不代表 wiki 团队已有的规划方向。
