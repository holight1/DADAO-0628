## 0. 结论提要（先说结论）

- **核心缺口是否真实存在：真实存在，但提案对"缺口有多大"的描述有一处
  实质性夸大**（见 §3-A）——普通访存指令能绕过的是 cfx 的"内部存储块"
  （SRAM，`cfxld`/`cfxst` 的操作对象），**不是**（也不能是）cfx 的
  cg/rc 寄存器组——寄存器组只能通过 `cfx2rd`/`cfx2rc` 专用指令以
  `cg:rc` 索引访问，wiki 全文没有任何地方把 cg/rc 寄存器映射进
  "核内地址空间"这条 48 位地址总线。提案 §1 用"直接读写目标 cfx 的
  核内**寄存器**/存储块"来描述攻击场景，这个措辞不准确。
- **核心缺口本身（普通访存绕开跨 cfx 屏蔽）在"内部存储块"这个正确
  范围内依然成立**，也依然值得修补——这一点提案的方向没有错。
- **但提案给出的具体修补机制（§2.2 的伪代码插入）在技术上不完整，
  按字面实现不会起到任何实际保护作用**（见 §3-B，这是本次评审发现的
  最严重问题）：插入点被嵌在"`if cause == CFXMEM`"分支内部，而
  `cause` 变成 `CFXMEM` 这件事本身（§2.1 第73行、cg7 第382行原文都
  明确写"**非法**访问时"）只在访问本身已经非法（地址不存在/写只读区）
  时才会发生——对一次**合法**的跨 cfx 访存（目标地址存在且权限允许），
  硬件根本不会进入这条异常分发伪代码，提案插入的检查永远不会被执行到。
  也就是说：提案真正想拦截的"合法但未经授权"的跨 cfx 访问，恰恰是
  当前插入位置**触发不到**的场景。要让这个掩码真正生效，必须同时修改
  §2.1/cg7 的"何时触发 CFXMEM"这条自然语言定义本身（把"被 mem_cfx_mask
  屏蔽"也列为触发 CFXMEM 的条件之一），而不只是修改 §5 步骤1的路由
  伪代码——提案完全没有触及前者。
- **除此之外，提案还有一处路由目标的自相矛盾**（见 §3-C）：新插入的
  `temp_cfx_code <= inner_cfx_code` 自称"与 reserved cfxcode 路由到
  当前 mode 对应 monitor 的既有惯例一致"，但 wiki 原文中 reserved
  cfxcode（以及六个功能调用掩码拦截）路由到的是**当前运行模式对应的
  monitor（`case inner_run_mode of ...`，即 cfx0-3）**，不是
  `inner_cfx_code`（当前正在执行的 cfx，可能是 cfx4-63 中任何一个）。
  这两者在"当前恰好在 cfx0-3 自己的 monitor 里"之外的场景（例如在
  `cfx_ptw` 处理程序里发生一次被新掩码拦截的访存）会给出不同的结果，
  提案对"一致"的断言是错的。
- **复位默认值"全1"、`rc12` 空闲槽位、排除范围（不涉及 PTBR 后的
  物理隔离）这三项设计选择，独立核实均成立**，没有发现问题。
- **一处纯引用行号笔误**（"第269行"应为"第271行"，见 §1 第2条）。
- 综上：**提案的"存在真实缺口"这一核心动机站得住脚（范围需收窄到
  "内部存储块"）；但提案当前给出的具体修补方案（§2.2）技术上不完整、
  不能达成其声称的效果，不能以现在的形式提交给 wiki 团队——需要先把
  触发条件的修改（而不只是路由的修改）补齐，并修正路由目标的表述。**

## 2. "缺口是否真实存在"——独立论证（不复述提案论证）

独立通读 wiki 第2章、第3章 cg0-cg7 全节、第5章异常进入/退出全部伪代码后，
得到以下独立论证链：

1. **`trap`/`escape`/`cfx2rd`/`cfx2rc`/`cfxld`/`cfxst` 六条指令的执行语义
   本身就是"总是进入异常分发流程"**——第5章步骤1第一分支
   `if instruction ∈ {TRAP, ESCAPE, CFXLD, CFXST, CFX2RD, CFX2RC}:` 在
   **每一次**这六条指令执行时都会走到，`cause` 是在这个分支内部被
   **赋值**的（`cause <= ILLI` / `cause <= CFXTRAP` 等）。这意味着这六个
   掩码（cg0-3/rc2-7）拦截的是"指令执行"这个动作本身，不管目标地址/
   寄存器合法与否，拦截判断总会发生。
2. **普通 `ldb`/`sto` 等访存指令则完全不同**：第5章步骤1的
   `elif mem_access:` 分支写的是 `if cause == CFXMEM:`——**读**一个已经
   确定的值，不是赋值。也就是说，这条分支只有在"内存访问单元已经
   判定这次访问非法"（`cause` 已经被置为 `CFXMEM`）之后才会被走到。
   而"何时判定为非法"由 §2.1 第73行和 cg7 第382行的自然语言定义，
   两处都明确写的是"**非法**访问时"（"访问不存在的地址，或试图写
   只读的区域"）——对一次目标地址存在且权限允许的**合法**访问，
   硬件根本不产生 `CFXMEM`，指令正常完成，读写照常发生，异常分发
   伪代码完全不会被触发。
3. 因此："功能调用类"指令与"访存类"指令在 wiki 现有设计里，对跨 cfx
   访问的拦截时机是**结构性不同**的：前者总是拦截、后者只在访问本身
   已经非法时才可能连带触发（并且现有的 `inner_cfx_mask`/
   `global_cfx_mask`——第694-695行——也只在这条本已非法的路径上生效，
   对合法访问同样起不到任何作用）。
4. **通读 §2.2.6"异常检查优先级"全表**（IALIGN/ILLI/UNDI/MALIGN/
   页表异常/FPEXCP）——CFXMEM 完全没有出现在这张优先级表里（合理，
   因为 CFXMEM 只在 PTBR 关闭的核内寻址下产生，跟这张表针对的
   虚拟地址空间异常路径是两套并行机制）。表里也没有任何条目能替代
   或覆盖"合法核内地址跨 cfx 访问"这个场景。
5. 逐字通读 cg0-cg7 全部寄存器表（第265-391行）、`escape` 安全约束
   （第664-676行）——**没有找到任何提案未提及的、能覆盖这条路径的
   既有机制**。

**独立结论：缺口真实存在。** 但范围需要修正（见下）：这条路径能碰到的
是"核内地址空间"里映射出来的内容——根据 cg7 第381行"内部存储块可
映射为核内地址空间；核内地址空间也可通过内部存储块机制进行访问；
具体方式由各核芯功能扩展自行定义"，以及 wiki 唯一给出的核内地址空间
实例（第66-68行，`cfx_power` 的复位向量，是取指区域不是寄存器区域）——
**cg/rc 寄存器组从未被 wiki 定义为可通过核内地址空间（48位地址总线）
访问**；`SimRISC-04-系统类指令.md` 第38、79-101行明确 `cfx2rd`/`cfx2rc`
用的是完全独立的 `cg:rc` 索引编码（指令域直接指定，不经过48位地址），
`cfxld`/`cfxst`（第111-123行）的内存侧地址 `rbhb` 也是走常规内存
地址，不是核内地址空间寻址。**核内地址空间目前唯一有据可查的内容是
"内部存储块"（cg7 SRAM）和 cfx_power 的复位向量，不包括寄存器组。**
提案 §1（第67行）"直接读写目标cfx的核内**寄存器**/存储块"这个表述
里的"寄存器"部分没有 wiki 依据，应改为只提"内部存储块"。

## 3. 设计质量与反例核查

### 3-A. 攻击场景描述过宽（次要问题，不影响缺口本身是否存在）

见上一节结论。提案 §1 的驱动场景（内核给不同驱动分不同 cfx，攻击者用
`sto` 读写"目标cfx的核内寄存器"）里"寄存器"一词没有 wiki 依据。真实
能被绕过的是"内部存储块"（SRAM，`cfxld`/`cfxst` 的操作对象，如果某
cfx 选择把它映射进核内地址空间的话）。这个范围收窄不影响"缺口存在"
这个结论，但会实质性削弱提案动机段落举的例子的说服力，提交前应改写。

**连带发现（次要，值得补充讨论）**：cg7 第381行用"可映射""也可通过"
这种措辞，说明"内部存储块"是否真的暴露在核内地址空间，**由每个 cfx
自行决定**（"具体方式由各核芯功能扩展自行定义"）。这意味着：
`cfxld_cfx_mask`/`cfxst_cfx_mask`（走 `cfxld`/`cfxst` 指令的既有掩码）
和提案新增的 `mem_cfx_mask`（走核内地址直接寻址）是**两条独立的门**，
如果某个 cfx 把同一块 SRAM 同时暴露在两条路径上，操作系统必须让两个
掩码配置保持一致的"松紧度"，否则较松的那个掩码会成为该数据实际的
安全下限（例如 `cfxld_cfx_mask` 配成拒绝，但 `mem_cfx_mask` 配成允许，
则 `cfxld`/`cfxst` 的屏蔽形同虚设）。提案 §2.3 提到"软件需要分别配置
这七个寄存器才能得到完整的...矩阵"，但没有点出这条"同一份数据被两条
门同时把守、配置不一致会让弱的一个决定实际安全强度"的具体风险，
建议补充讨论。

### 3-B. 插入点技术上不完整——本提案最严重的问题

见 §0/§2 已充分论证：`§2.2` 的伪代码插入点被嵌在 `if cause == CFXMEM`
分支**内部**，而这个分支只有在访问已经被判定为非法时才会执行到。
对提案真正想拦截的"目标地址合法、但发起方 mode 未被 `mem_cfx_mask`
授权"这一类访问，`cause` 根本不会变成 `CFXMEM`，异常分发伪代码不会
被进入，提案插入的检查是死代码。

**这不是"要不要新增异常原因编号"的问题（那只是次要的设计偏好问题，
见 3-C），而是插入位置本身选错了层次**：提案需要做的是修改 §2.1
（第73行）和 cg7（第382行）里"何时判定为非法"这条自然语言定义，
把"被对应 `mem_cfx_mask` 屏蔽"也列为使访问变为非法（从而使 `cause`
真正被置为 `CFXMEM`）的条件之一，然后才谈得上第5章步骤1的路由伪代码
要不要改。提案完全没有触及前者，只改了后者，属于**改了下游、漏了
上游**。

按照本任务的严重度分级：这个问题**不会让"缺口存在"这个核心动机站
不住**（缺口依然真实存在），但**会让提案给出的具体修补方案完全无效
——如果 wiki 团队按提案字面实现，`mem_cfx_mask` 会被引入寄存器空间、
软件也能读写它，但它永远不会真正拦截任何访问**，这是一个必须在提交
前修复的实质性技术缺陷。

### 3-C. 路由目标与自身注释矛盾（实质性问题，独立于 3-B）

提案插入的伪代码：

```
temp_cfx_code <= inner_cfx_code  ; 路由回当前 cfx 自己的 monitor
                                 ; （与 reserved cfxcode 路由到当前
                                 ; mode 对应 monitor 的既有惯例一致）
```

核实 wiki 原文中"reserved cfxcode 路由到当前 mode 对应 monitor"的
**实际写法**（第747-753行，以及六个功能调用掩码拦截的第721-728行）：

```
case inner_run_mode of
    U-mode: temp_cfx_code <= 0
    J-mode: temp_cfx_code <= 1
    S-mode: temp_cfx_code <= 2
    H-mode: temp_cfx_code <= 3
```

这是按**当前运行模式**路由到 cfx0-3（mode monitor），**不是**
`inner_cfx_code`（当前正在执行的 cfx，可以是 cfx4-63 中任意一个）。
`inner_cfx_code` 和"当前 mode 对应的 monitor"只有在 CPU 恰好正在
cfx0-3 自己的 monitor 里执行时才相等；一旦当前正在 `cfx_ptw`/
`cfx_timer` 等非 monitor 的 cfx 的处理程序里执行（这是完全正常的
场景，例如 PTW 处理页表异常时的代码本身也可能发出一次访存指令），
`inner_cfx_code` 就是该 cfx 的编号（如4），与 mode monitor（0-3）
不同——两种路由方式在这种场景下会给出不同的目标 cfx。

**提案对"一致"的自我断言是错的**，这不是笔误级别（会实际影响硬件
行为落到哪个 cfx 的异常处理程序），需要在提交前明确：新掩码拦截后
到底应该路由到"当前 mode 的 monitor"（与六个既有掩码保持一致，但
这样也该像它们一样把 `cause` 改成 `ILLI` 而不是保留 `CFXMEM`），
还是路由到"当前正在执行的 cfx 自己"（`inner_cfx_code`，这是提案
实际写的路由目标，但这个选择需要独立论证为什么和六个既有掩码的
既定惯例不同，提案目前没有论证，只是错误地声称两者一致）。

### 3-D. 复位默认值、寄存器槽位、排除范围——独立核实通过

- **复位默认值"全1"**：独立核对 wiki 第275-281行（cg0 六个掩码）、
  第299-305行（cg1）、第319-325行（cg2）——`user/jail/supv global
  cfx mask` 及 `cfx2rd/cfx2rc/cfxld/cfxst/trap/escape cfx mask`
  **全部**复位值为"全1"，与提案声称一致。**核实通过，不是提案自己
  假设的。**
- **`rc12` 是否真的空闲**：逐行核对 cg0（第275-285行）rc1-11 全部
  被占用（global/cfx2rd/cfx2rc/cfxld/cfxst/trap/escape/switch_run_mode/
  switch_cfx_mask/excp_vector/excp_cause_mask），rc12 及以后确实
  未出现在表中。**核实通过。** 附带发现一个提案没提到、但不构成
  问题的细节：cg0-3 的 `rc0` 在表中同样未出现（表格从 rc1 开始），
  也是一个空闲槽位；提案选 rc12（延续 1-11 的顺序）而非 rc0 是合理
  选择，但wiki团队最终若倾向 rc0 也不会与本提案的技术设计冲突，
  只是槽位号不同，值得在开放问题里提一句（提案 §4 第2条已经承认
  槽位分配权在 wiki 团队，这个附带发现只是让这句话更具体）。
- **复用 CFXMEM 而不新增异常原因**：见 3-C——这个选择本身（是否
  分配新原因编号）不是问题，问题是"复用 CFXMEM 但路由方式却抄六个
  掩码的惯例"这个组合在内部不自洽（六个掩码惯例是"cause 变
  ILLI + 路由到 mode monitor"，提案却是"cause 留 CFXMEM +
  路由到 inner_cfx_code"，两边各取一半、拼出一个 wiki 里不存在的
  第三种路由方式）。
- **排除范围**（不涉及 PTBR 开启后的物理内存隔离）：独立重读
  §2.2.1-2.2.4（虚实地址转换）确认这是完全独立的另一套机制
  （`cfx_ptw_pahi`/`pthi`/权限位图），提案把这个排除在范围外是
  合理的范围划分，没有发现"新掩码带来意外副作用破坏 PTBR 场景"
  的迹象——两套机制在地址译码的最前端就已经分岔（是否 PTBR
  开启决定走哪一套），互不影响。**核实通过。**
- **"不要求现有实现做任何改动"**：这一条按本任务约束（不得涉及
  QEMU/gem5/Linux 源码）无法在源码层面独立核实内核是否真的从未
  使用核内地址跨 cfx 访存。但从纯逻辑角度：`mem_cfx_mask` 是一个
  wiki 从未定义过、当前 QEMU/gem5 都没有实现的**全新寄存器**，
  在它被 wiki 采纳、被实现之前，现有 K1-K3 的任何软硬件都不可能
  依赖或受它影响——这一点在逻辑上必然成立，不需要读源码验证。
  至于"内核代码是否真的只通过 cfx2rd/cfx2rc 访问其它 cfx 寄存器、
  从未使用核内地址直接寻址"这个更具体的经验性断言，本次评审按
  任务约束未做源码层面核实，如实标注为未验证（不是"已核实为真"）。

### 3-E. 层级不一致场景（hypv 掩码全开、supv 掩码全关）——不是新问题

独立检查 wiki 是否在任何地方要求或暗示四个运行模式的掩码之间存在
"高权限模式必须比低权限模式更严格/更宽松"这类层级约束——**没有找到
任何这样的表述**。cg0-cg3（第265-336行）逐个模式独立定义、独立读写，
现有六个掩码今天就已经可以被配置成"hypv 全开、supv 全关"这种反直觉
组合，wiki 从未禁止或警告这种配置。因此，这个场景**不是本提案引入
的新问题**，而是整个"按模式独立配置掩码"这一既有设计的固有特性——
新掩码继承这个特性是内部一致的，不需要额外论证层级继承关系。提案
没有讨论这一点是合理的省略（不讨论一个既有设计早已存在、且不算
缺陷的特性，不算遗漏）。

## 4. 问题分级汇总

**A. 会让提案"当前给出的具体修补机制"失效的实质性问题**（不影响
"缺口存在"这个核心动机，但意味着提案不能以现在的形式提交）：

1. §3-B：插入点选错层次——只改了 §5 路由伪代码，没有同步修改
   §2.1/cg7 定义"何时判定为非法访问"的自然语言条件，导致合法但
   未授权的跨 cfx 访问永远不会触发 `CFXMEM`，新掩码形同虚设。
2. §3-C：新插入路由 `temp_cfx_code <= inner_cfx_code` 与其自称
   "和 reserved cfxcode 路由到 mode monitor 的既有惯例一致"矛盾——
   两者在 `inner_cfx_code` 不等于 mode monitor 编号时（例如在
   `cfx_ptw` 处理程序内触发）会给出不同结果，需要重新论证到底该
   走哪种路由，而不是错误地声称两者相同。

**B. 值得补充讨论但不影响核心论点的次要问题**：

3. §3-A：动机场景描述过宽——"直接读写目标cfx的核内寄存器"里的
   "寄存器"没有 wiki 依据，真实能被绕过的只有"内部存储块"
   （cg/rc 寄存器组只能通过 cfx2rd/cfx2rc 访问，与核内地址空间
   是不同的寻址机制），建议改写动机段落措辞。
4. §3-A 连带发现：当某 cfx 把内部存储块同时暴露在
   "cfxld/cfxst + 核内地址直接寻址"两条路径时，两个掩码
   （`cfxld_cfx_mask`/`cfxst_cfx_mask` 与新的 `mem_cfx_mask`）
   配置不一致会让较松的一个决定实际安全强度，建议补充这条
   操作规范提示。
5. §3-D：rc0 也是一个空闲槽位，可以在开放问题里提一句作为
   wiki 团队的备选（不是必须改）。

**C. 纯文字/引用层面的笔误**：

6. §2.1 正文"第269行'以下11个寄存器'"应为"第271行"（第269行是
   cg0 小节标题，"以下11个寄存器"这句话本身在271行）。范围引用
   "第269-281行"没有问题。

**未发现问题、核实通过的部分**：复位默认值全1（一致）、`rc12` 空闲
（一致）、PTBR 排除范围合理、层级不一致场景不是新问题、六处 wiki
引用中五处逐字准确。
